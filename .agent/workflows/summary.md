---
description: Sinh summary files cho base_knowledge (summary_standards.md, summary_structures.md) với phase tagging
---

Sinh summary files tổng hợp metadata cho `base_knowledge/`. Các file này phục vụ `feat-init` để sinh `feat_overview.md` có phase tagging — giúp `feat-propose` và `feat-apply` chỉ đọc files cần thiết cho phase tương ứng, tiết kiệm token.

**Output:**
- `base_knowledge/standards/summary_standards.md`
- `base_knowledge/structures/summary_structures.md`

---

**Input**: `/summary --knowledge`

Nếu không có arg `--knowledge` → nhắc user: "Hiện tại chỉ hỗ trợ `--knowledge`. Chạy `/summary --knowledge` để sinh summary cho base_knowledge."

**Steps**

## 1. Kiểm tra base_knowledge tồn tại

Check `base_knowledge/` directory tồn tại.
- **Nếu KHÔNG tồn tại** → HALT: "base_knowledge/ không tồn tại. Hãy chạy /initial-project trước."
- **Nếu tồn tại** → tiếp tục.

## 2. Kiểm tra summary files đã tồn tại

Check `base_knowledge/standards/summary_standards.md` và `base_knowledge/structures/summary_structures.md`.
- **Nếu đã tồn tại** → hỏi user: "Summary files đã tồn tại. Ghi đè? (Y/N)". Nếu user từ chối → STOP.
- **Nếu CHƯA tồn tại** → tiếp tục.

## 3. Scan và đọc Standards

a. List tất cả `.md` files trong `base_knowledge/standards/` (loại trừ `README.md` và `requirement_standards.md`).

b. **ĐỌC NỘI DUNG** từng file — trích xuất:
   - **Purpose**: File này dùng làm gì (1 câu)
   - **Key patterns**: 3-5 patterns/rules chính (bullet points ngắn)
   - **Phase assignment**: Gán phase mặc định theo bảng heuristic (xem Step 5)

## 4. Scan và đọc Structures

a. List tất cả `.md` files trong `base_knowledge/structures/` (loại trừ `README.md` và `requirement_structures.md`).

b. **ĐỌC NỘI DUNG** từng file — trích xuất tương tự Step 3.

## 5. Gán Phase mặc định (Heuristic Table)

Sử dụng bảng heuristic sau để gán phase mặc định. Nếu file không match pattern nào → mặc định `propose, apply`.

**Standards:**

| File pattern | Default phase | Lý do |
|---|---|---|
| `coding_standard.md` | propose, apply | Cần cho cả thiết kế (naming convention) lẫn code |
| `logging_standard.md` | apply | Chỉ cần khi viết code |
| `error_handling_standard.md` | apply | Chỉ cần khi viết code |
| `dto_standard.md` | apply | Chỉ cần khi viết code |
| `database_standard.md` | apply | Chỉ cần khi viết code |
| `error_code_standard.md` | apply | Chỉ cần khi viết code |
| `api_standard.md` | propose | Cần cho thiết kế API ở proposal/design |
| `security_standard.md` | propose, apply | Cần ở cả planning lẫn implementation |
| `*_integration_*.md` | propose, apply | Cần ở cả thiết kế integration lẫn code |
| `financial_flow_*.md` | propose | Cần cho thiết kế luồng giao dịch |
| `non_financial_flow_*.md` | propose | Cần cho thiết kế luồng phi giao dịch |

**Structures:**

| File pattern | Default phase | Lý do |
|---|---|---|
| `system_overview.md` | propose | Cần cho context hệ thống khi thiết kế |
| Service-specific (`*-service.md`, etc.) | propose, apply | Cần ở cả thiết kế lẫn implementation |

**Rules (common_rules/):**

| File pattern | Default phase | Lý do |
|---|---|---|
| `rule_planing_feature.md` | propose | Chỉ dùng cho planning/design/spec |
| `rule_security.md` | propose, apply | Cần ở cả planning lẫn code |
| `rule_generate_srs.md` | archive | Chỉ dùng khi sinh SRS |
| `rule_change_trans_status.md` | apply | Chỉ cần khi viết code xử lý trạng thái |

> **Mặc định**: Files không match bất kỳ pattern nào → `propose, apply`.

## 6. Sinh Summary Files

### 6a. Sinh `base_knowledge/standards/summary_standards.md`

```markdown
# Summary: Standards

> Generated by `/summary --knowledge` on YYYY-MM-DD HH:mm:ss
> Source: `base_knowledge/standards/`
> Purpose: Cung cấp thông tin tổng quan và phase tagging cho `feat-init`. KHÔNG thay thế cho việc đọc file gốc.

## Standards Index

| # | File | Summary | Phase |
|---|------|---------|-------|
| 1 | [filename].md | [50-80 từ tóm tắt key patterns/purpose] | [phase1, phase2] |
| ... | ... | ... | ... |

## Phase Legend

- **propose**: File được đọc trong `feat-propose` — thiết kế, planning, API contracts
- **apply**: File được đọc trong `feat-apply` — coding conventions, error handling, logging
- **archive**: File được đọc trong `feat-archive` — SRS generation, documentation sync
```

### 6b. Sinh `base_knowledge/structures/summary_structures.md`

```markdown
# Summary: Structures

> Generated by `/summary --knowledge` on YYYY-MM-DD HH:mm:ss
> Source: `base_knowledge/structures/`
> Purpose: Cung cấp thông tin tổng quan và phase tagging cho `feat-init`. KHÔNG thay thế cho việc đọc file gốc.

## Structures Index

| # | File | Summary | Phase |
|---|------|---------|-------|
| 1 | [filename].md | [50-80 từ tóm tắt key content] | [phase1, phase2] |
| ... | ... | ... | ... |

## Phase Legend

- **propose**: File được đọc trong `feat-propose` — system context, architecture overview
- **apply**: File được đọc trong `feat-apply` — service details, processing flows
- **archive**: File được đọc trong `feat-archive` — documentation sync reference
```

## 7. Sinh Summary cho Rules (Bổ sung)

Tương tự, scan `base_knowledge/common_rules/` (loại trừ `README.md`) và thêm bảng Rules vào **cuối** `summary_standards.md`:

```markdown
## Rules Index

> Source: `base_knowledge/common_rules/`

| # | File | Summary | Phase |
|---|------|---------|-------|
| 1 | [filename].md | [50-80 từ tóm tắt] | [phase1, phase2] |
```

> **Lý do gộp vào summary_standards.md**: Rules và Standards đều là tài liệu quy tắc — gộp giúp `feat-init` chỉ cần đọc 2 files (standards+rules summary, structures summary) thay vì 3.

## 8. Hiển thị kết quả

```
## Summary Generated

**Files created:**
- base_knowledge/standards/summary_standards.md (N standards + M rules indexed)
- base_knowledge/structures/summary_structures.md (K structures indexed)

**Phase distribution:**
- propose: X files
- apply: Y files
- archive: Z files
- propose+apply: W files

Run `/feat-init` to use phase tagging in your next feature.
```

---

**Guardrails**
- **MUST** đọc nội dung thực tế của từng file — KHÔNG được chỉ đọc filename rồi đoán nội dung
- **MUST** giữ summary mỗi file trong khoảng 50-80 từ — đủ để hiểu purpose, KHÔNG quá dài
- **MUST** sử dụng bảng heuristic ở Step 5 cho phase assignment — KHÔNG tự đoán
- **MUST** hỏi user trước khi overwrite summary files đã tồn tại
- **DO NOT** sửa bất kỳ file nào trong `standards/`, `structures/`, `common_rules/` — chỉ ĐỌC và sinh summary
- **DO NOT** thêm files không tồn tại vào summary — chỉ index files thực sự có trên filesystem
- Files mới không match heuristic → gán mặc định `propose, apply`
