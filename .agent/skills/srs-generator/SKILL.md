Generate an SRS (Software Requirements Specification) document for a change. Collects source of truth from change artifacts, tracking artifacts, and source code, then generates SRS following the template in `base_knowledge/common_rules/rule_generate_srs.md`.

**Input**: Optionally specify a change name, metadata ID, or nothing (auto-detect).

**Steps**

## 1. Input Resolution

Resolve which change to generate SRS for using 3 modes:

### 1a. Change Name (direct lookup)

If user provides a change name:
- Look up `openspec/changes/<name>/`
- If not found in active, search `openspec/changes/archive/` for directories ending with `-<name>`
- If found → proceed
- If not found → report error and list available changes

### 1b. Metadata ID (scan)

If user provides a metadata ID:
- Scan all `metadata.yaml` files in `openspec/changes/` (active + archive)
- Match against the `id` field
- If found → proceed
- If not found → report error and list available changes

### 1c. No Input (auto-detect)

If no input provided:
- Run `openspec list --json` to get active changes
- **1 active change** → auto-select, announce: "Auto-selected change: `<name>`"
- **Multiple active** → list all and ask user to select
- **0 active** → scan archived changes, list and ask user to select

Always announce: "Generating SRS for change: `<name>`"

## 2. Load SRS Template Rule

Read the SRS template from `base_knowledge/common_rules/rule_generate_srs.md`.

Parse:
- Section definitions (1–6)
- `[REQUIRED]` / `[OPTIONAL]` markers for each section
- Writing principles and rules
- Source-to-section mapping table

> **If rule file is missing**: HALT — "SRS template rule file not found at `base_knowledge/common_rules/rule_generate_srs.md`. Please create it first." STOP.

Show: "Loaded SRS template: N required sections, M optional sections."

## 3. Collect Source of Truth

Collect context from 3 layers, adapting to whatever change type is available.

### Layer 1: Change Artifacts (MUST have at least 1)

Read whichever exist in the change directory:

| File | Purpose |
|------|---------|
| `proposal.md` | What was proposed and why |
| `design.md` | Technical design decisions |
| `specs/*.md` or `specs/*/spec.md` | Detailed requirements |
| `tasks.md` | Implementation plan and status |
| `tech_requirement.md` | Condensed technical rules |
| `feat_overview.md` | Feature overview and scope |
| `metadata.yaml` | Change metadata |

> **If NO change artifacts found**: HALT — "No change artifacts found in `<change-dir>`. Cannot generate SRS without context." STOP.

### Layer 2: Tracking Artifacts (optional — enriches SRS)

Read if they exist:

| File | Maps To SRS Section |
|------|---------------------|
| `todo-uncover.md` | Section 6 — Known Limitations |
| `new-apis.md` | Section 4 — External Interface Requirements |
| `delta-spec.md` | Section 3 — Functional Requirement adjustments |

### Layer 3: Source Code (primary source of truth for functional requirements)

Scan the implementation to verify and enrich functional requirements:

a. **Identify changed files**: Use `git diff` or check `tasks.md` for file references
b. **Scan Controller classes** → Extract API endpoints, HTTP methods, request/response schemas
c. **Scan Service classes** → Extract business logic, validation rules, processing flows
d. **Scan Entity/DTO classes** → Extract data models, field definitions
e. **Scan Config files** → Extract system configuration, feature flags

> **Optimization**: Prioritize reading artifacts first (Layer 1 + 2). Only scan code (Layer 3) for sections that need verification or enrichment — typically Section 3 (Functional Requirements) and Section 4 (External Interfaces).

Show progress:
```
Source collection complete:
- Change artifacts: N files loaded
- Tracking artifacts: M files loaded (or: none found)
- Source code: K files scanned (or: skipped — artifacts sufficient)
```

## 4. Generate SRS Document

Generate `srs.md` following the template from Step 2 and using the context from Step 3.

### 4a. Determine Output Location

```
If change is active:   openspec/changes/<name>/srs.md
If change is archived: openspec/changes/archive/<archive-dir-name>/srs.md
```

### 4b. Generate Each Section

For each section in the template:
- **If `[REQUIRED]`**: MUST generate content. If insufficient context → generate with `[TODO: ...]` markers
- **If `[OPTIONAL]`**: Generate if sufficient context exists. Skip entirely if not applicable (do NOT leave empty sections)

### 4c. SRS Header

Start the document with:
```markdown
# SRS: <Feature/Change Name>

> Generated by srs-generator on YYYY-MM-DD HH:mm:ss
> Source change: `<change-name>` (ID: `<metadata-id>` if available)
```

### 4d. Generation Rules

- ALL functional requirements (Section 3) MUST be derived from **actual code or artifacts** — NOT from assumptions
- Each System Feature MUST include **Test Scenarios** (Section 3.N.4) — no exceptions
- MUST use **business language** (audience: tester/client) — avoid class names, package paths, internal method names
- MUST cross-reference with `proposal.md` and `specs/` for traceability
- Apply the **Source-to-Section Mapping** from the rule file when tracking artifacts are available
- For `[OPTIONAL]` sections without sufficient data, omit the section entirely

## 5. Show Results

After generating, display:

```
## SRS Generated

**Change:** <change-name>
**Output:** <output-path>

### Sections Generated
- [V] 1. Introduction [REQUIRED]
- [V] 2. Overall Description [REQUIRED]
- [V] 3. System Features — N features documented [REQUIRED]
- [V] 4. External Interface Requirements [OPTIONAL]  (or: [—] Skipped)
- [V] 5. Non-functional Requirements [OPTIONAL]  (or: [—] Skipped)
- [V] 6. Other Requirements [OPTIONAL]  (or: [—] Skipped)

### Sources Used
- Change artifacts: proposal.md, design.md, specs/*, tasks.md
- Tracking artifacts: todo-uncover.md, new-apis.md (or: none)
- Source code: N files scanned (or: not scanned)

### TODOs (if any)
- [TODO] items that need manual completion
```

---

**Guardrails**
- MUST read `rule_generate_srs.md` before generating — HALT if missing
- MUST have at least 1 change artifact to generate from — HALT if none found
- MUST derive functional requirements from actual artifacts/code — never assume
- MUST include test scenarios for every System Feature in Section 3
- MUST write in business language for tester/client audience
- MUST respect `[REQUIRED]` / `[OPTIONAL]` markers from the rule file
- Do NOT generate empty sections — either populate or omit `[OPTIONAL]` ones
- Do NOT modify any existing change artifacts — SRS is a new output file
- Do NOT require all artifacts to exist — adapt to whatever is available
- If source code is not accessible or not applicable (e.g., documentation-only change), skip Layer 3 and note in the output
