Archive a completed Change Request (CR). Extends `opsx-archive` with code-vs-documentation sync check, final compare-logic update, changelog generation, CR tracking artifact preservation, and knowledge export advisory.

**Input**: Optionally specify a change name. If omitted, infer from conversation context or prompt.

**Steps**

## 1. Identify the Change to Archive

If no change name provided, scan `openspec/changes/` for active (non-archived) changes.

- Present the list and let the user select.
- If only one active change exists, confirm with the user before proceeding.

**IMPORTANT**: Do NOT guess or auto-select a change. Always let the user confirm.

## 2. Check Artifact Completion Status

Run `openspec status --change "<name>" --json` to check artifact completion.

Parse the JSON to understand:
- `schemaName`: The workflow being used
- `artifacts`: List of artifacts with their status (`done` or other)

**If any artifacts are not `done`:**
- Display warning listing incomplete artifacts
- Prompt user for confirmation to continue
- Proceed if user confirms

## 3. Check Task Completion Status

Read the tasks file (`cr-tasks.md` or `tasks.md`) to check for incomplete tasks.

Count tasks marked with `- [ ]` (incomplete) vs `- [x]` (complete).

**If incomplete tasks found:**
- Display warning showing count: `"Warning: X of Y tasks are still incomplete."`
- Ask user for confirmation to continue.
- Proceed only if user confirms.

**If no tasks file exists:** Proceed without task-related warning.

## 4. Code-vs-Documentation Sync Check

Before archiving, verify that the documentation accurately reflects what was actually implemented.

### 4a. Identify Changed Files

Use `git diff` or manual file scanning to find modified/new files related to this change.
Focus on Controller, Service, Model/Entity, and Config layers.

### 4b. Read All Change Documents

Read the existing CR artifacts:
- `cr-proposal.md` — What was proposed
- `cr-design.md` — How it was designed
- `cr-tasks.md` — Implementation plan
- `current-code-logic.md` — Pre-CR code state
- `compare-logic.md` — Logic comparison

### 4c. Compare Code vs. Documentation

For each significant implementation detail, check if the documentation describes it accurately:

| Check Item | What to Compare |
|-----------|----------------|
| Endpoints | Documented paths/methods vs actual `@RequestMapping` annotations |
| Service methods | Documented method signatures vs actual implementations |
| Entities/DTOs | Documented fields vs actual field definitions |
| Business logic | Documented flows vs actual control flow |
| Error handling | Documented error codes vs actual `Constants.ResCode` usage |
| Config keys | Documented config usage vs actual `getConfig()` calls |

### 4d. Handle Results

**If ALL MATCH:**
```
[OK] Documentation is in sync with source code. No corrections needed.
```

**If MISMATCHES FOUND:**

a. Auto-correct each mismatched document — edit documentation to reflect actual implementation.

b. Add warning markers at each corrected location:
```markdown
> [!WARNING]
> **Auto-corrected during archive (YYYY-MM-DD)**
> Original documentation stated: [original description]
> Actual implementation: [what was really implemented]
```

c. Generate sync report showing all corrections.

d. Prompt user: "Documentation has been auto-corrected. Review and confirm to proceed."

## 5. Update `compare-logic.md` (Final State)

Update the logic comparison table to reflect the **post-implementation** state.

For each row in the comparison table, add/update the final status:

```markdown
| # | Logic Point | Before CR | After CR | Status | Note |
|---|------------|-----------|----------|--------|------|
| 1 | [description] | [from current-code-logic.md] | [actual final state] | [V] Resolved / [!] Partial / [NEW] Added | [notes] |
```

Add a summary section:
```markdown
## Final Resolution Summary
- Gaps closed: N of M
- New behaviors added: K
- Behaviors removed: J
- Remaining gaps: L (if any — with justification)
```

## 6. Collect change-apply Tracking Artifacts

Check for tracking artifacts generated by `change-propose` and `change-apply` in `openspec/changes/<name>/`:

| File | Description |
|------|-------------|
| `metadata.yaml` | Change metadata (name, services, endpoints, timestamps, references) |
| `regression-check.md` | Backward compatibility verification |
| `migration-note.md` | Config/DB/API deployment changes |
| `delta-spec.md` | Behavioral delta analysis |

List which tracking artifacts exist. `metadata.yaml` should always be present (generated during `change-propose`). These files will travel with the change directory during archive move.

## 7. Generate `changelog.md`

Create a comprehensive changelog summarizing the entire CR lifecycle:

```markdown
# Changelog: <CR Name>

**Date**: YYYY-MM-DD
**Type**: Change Request
**Status**: Archived

## Summary
[1-2 sentence summary from cr-proposal.md]

## Changes

### Added
- [New features, endpoints, entities, configs added]

### Modified
- [Existing features, logic, schemas modified]

### Removed
- [Deprecated features, endpoints, configs removed]

### Fixed
- [Bug fixes applied during CR]

## Migration Requirements
[Summary from migration-note.md — or "No migration required"]

### Config Changes
| Key | Change | Notes |
|-----|--------|-------|

### Database Changes
| Table | Change | Notes |
|-------|--------|-------|

### API Changes
| Endpoint | Change | Breaking? |
|----------|--------|-----------|

## Regression Impact
[Summary from regression-check.md]
- Total behaviors verified: N
- Intentionally changed: M
- Unplanned impacts: K

## Files Changed
[List of primary files modified/added/removed during implementation]

## Related Documents
- `cr-proposal.md` — CR proposal and impact analysis
- `cr-design.md` — Technical design
- `cr-tasks.md` — Implementation tasks
- `current-code-logic.md` — Pre-CR code state snapshot
- `compare-logic.md` — Logic comparison (before vs after)
- `regression-check.md` — Backward compatibility report
- `migration-note.md` — Deployment migration guide
```

## 8. Assess Delta Spec Sync State

Check for delta specs at `openspec/changes/<name>/specs/`. If none exist, proceed without sync prompt.

**If delta specs exist:**
- Compare each delta spec with its corresponding main spec
- Show summary of changes
- Prompt: "Sync now (recommended)" or "Archive without syncing"

If user chooses sync, perform agent-driven intelligent merge.

## 9. Knowledge Export Advisory

Before archiving, analyze whether this CR has implications for `base_knowledge/`:

### 9a. Check for Standards Impact

Does this CR change established patterns?
- New error codes or error handling pattern? → May affect `error_handling_standard.md`
- New logging patterns? → May affect `logging_standard.md`
- New coding conventions? → May affect `coding_standard.md`

### 9b. Check for Structure Impact

Does this CR change architecture?
- New service/module added? → May need new structure doc
- Service dependencies changed? → May affect existing structure docs
- New infrastructure components? → May affect `system_overview.md`

### 9c. Report (WARN ONLY — do NOT auto-update)

**If NO impact detected:**
```
[OK] No impact on base_knowledge/ detected. Proceeding with archive.
```

**If potential impact detected:**

```
> [!WARNING]
> **Potential base_knowledge/ Impact Detected**
>
> This CR may affect the following base knowledge documents:
>
> | Document | Reason |
> |----------|--------|
> | `standards/error_handling_standard.md` | New error code pattern ERR_XXX introduced |
> | `structures/payment-service.md` | New dependency on notification-service added |
>
> **Action Required**: After archiving, consider running `/initial-project` to update
> affected documents, or manually update them.
>
> Proceeding with archive...
```

**CRITICAL**: Do NOT auto-update `base_knowledge/` files. Only warn the user. This saves tokens and avoids out-of-context issues.

## 10. Perform the Archive

a. **Create archive directory** if it doesn't exist:
```bash
mkdir -p openspec/changes/archive
```

b. **Generate target name** using current date: `YYYY-MM-DD-<change-name>`

c. **Check if target already exists:**
- If yes: Fail with error, suggest renaming.
- If no: Move the change directory.

```bash
mv openspec/changes/<name> openspec/changes/archive/YYYY-MM-DD-<name>
```

d. **Copy changelog to `base_knowledge/changelogs/`** (create directory if needed):
```bash
mkdir -p base_knowledge/changelogs
cp openspec/changes/archive/YYYY-MM-DD-<name>/changelog.md base_knowledge/changelogs/YYYY-MM-DD-<name>.md
```

e. **Verify** the move and copy were successful.

## 11. Display Archive Summary

```
## Archive Complete

**Change:** <change-name>
**Archived to:** openspec/changes/archive/YYYY-MM-DD-<name>/
**Changelog copied to:** base_knowledge/changelogs/YYYY-MM-DD-<name>.md

### Documentation Sync Check
[OK] Documentation is in sync (or: N corrections applied)

### Compare-Logic Final State
- Gaps closed: N of M
- New behaviors: K
- Remaining gaps: L

### Task Status
All X tasks complete. (or: Archived with Y incomplete tasks)

### CR Tracking Artifacts Archived
- regression-check.md [OK] (or: not found)
- migration-note.md [OK] (or: not found)
- delta-spec.md [OK] (or: not found)
- changelog.md [OK]

### Knowledge Export Advisory
[OK] No base_knowledge/ impact (or: [!] N documents may need updating — see warning above)

### Specs
Synced to main specs / Sync skipped / No delta specs
```

---

**Guardrails**
- **MUST** perform code-vs-documentation sync check (Step 4) before archiving
- **MUST** update `compare-logic.md` with final post-implementation state (Step 5)
- **MUST** generate `changelog.md` (Step 7) — this is the primary knowledge output
- **MUST** copy `changelog.md` to `base_knowledge/changelogs/`
- **MUST** only edit documentation to match code — NEVER edit code to match documentation
- **MUST** add `> [!WARNING]` markers on every auto-corrected section
- **MUST NOT** auto-update `base_knowledge/standards/` or `base_knowledge/structures/` — only warn
- **MUST** prompt user after corrections before proceeding to archive
- Do NOT auto-select a change — always let the user confirm
- Do NOT modify existing correct content in documents — only correct inaccurate sections
- Preserve all existing files when moving to archive (entire directory moves, including tracking artifacts)
- Verify the archive directory and changelog copy exist after operations
